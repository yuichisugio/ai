## 入力の収集（憶測で書かない）

1. PRのURLが与えられている場合は、その変更を読む。ない場合は、現在のブランチで `git diff <base>...HEAD` と変更ファイル群を読む
2. ブランチ名・コミットメッセージから意図の手がかりを得る
3. 該当範囲の`CLAUDE.md`,`AGENTS.md`でプロジェクト文脈を補う

## descの目的

レビュアーの頭の中に、コードを書いた本人と同じメンタルモデルを
再構築する。判断点を列挙するのではなく、レビュアーが変更の全容を
把握し、読みながら自力で懸念に気づける状態を作る。
descは「渡されたタスク説明」と「コードを読めば分かること」の
間にある溝を埋める文書である。

## 粒度の基準（最重要）

- 網羅: 変更のどの部分もdesc上で位置づけられること。
  「説明されていないファイル群」を残さない。
- 詳細: 場所で濃淡をつける。判断点・自信のない箇所は濃く、
  機械的な部分は一行で触れる。均一な詳細度にしない。
- 合否テスト: descを読んだレビュアーが diffを開く前に各部分の
  挙動を予測でき、読みながら「予想と違う/これで大丈夫か」が
  立ち上がる粒度。予測できない=穴、diffの再ナレーション=冗長。

## 書き方の核

1. タスクをどう具体化したか: 渡された抽象的な要求を、著者が
   どう解釈し何を具体的に確定させたかを書く（溝の本体）。
2. 全体像: 主要な部品とその関係を地図として示す。
3. 読む順序: どこから読むべきか、依存の幹を示す。
4. 動作の流れ: 代表的な1ケースを入力から結果まで、変更した
   部品を実行順/データフロー順に1本なぞる(モデル構築の中核)。
   ファイル単位ではなくフロー単位で語る。
5. 自信マップ: 各領域を「自信あり/怪しい/意図的に変」で示す。
   - 怪しい: 著者自身が不安な点を正直に出す(懸念を引き出す)
   - 意図的に変: diffで奇妙に見えるが狙い通りの箇所(指摘抑制)
     弁明で判断を守ろうとしない。弱点をさらけ出す方を優先する。

## 禁止

- ファイル列挙・行数・シグネチャの再掲(diffにある変更そのもの)
- 均一に薄い/均一に濃い記述
- 意図が不明な箇所の捏造 → `<!-- TODO -->` でユーザーに確認

## 出力

- 日本語・Markdown・冒頭TL;DR
- 構成: ## TL;DR / ## どう捉えたか / ## 全体像 /
  ## 読む順序 / ## 動作の流れ / ## 主要な判断(L2) /
  ## 自信マップ / ## スコープ外 / ## 動作確認
- 長い節は <details> で畳む

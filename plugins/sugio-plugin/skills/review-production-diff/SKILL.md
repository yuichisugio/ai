# Production差分レビュー

productionブランチと現在のブランチの差分を、コード品質・セキュリティ・保守性・テスト・画面影響・本番投入準備の観点で注意深くレビューする。

このSkillの役割はレビューと報告であり、ユーザーが明示するまでコード編集やコミットは行わない。

## レビュー依頼として扱う内容

ユーザーから追加の観点、画面名、PR、Issue、コミット範囲、確認中の画面、気になる挙動が渡された場合は、それを重点観点として扱う。

特に次の依頼が含まれているものとしてレビューする。

- `production`ブランチと現在のブランチの差分について、以下の観点で注意深くレビューする
- レビューした内容や、使用中の画面に関する機能変更を網羅的にもれなく報告する
- 変更点が多い場合は、コミットごと、見る観点ごとにサブエージェントを積極的に活用して見逃しを減らす
- 細かいところも上限なく、数十個以上になってもよいので網羅的に指摘する

ただし、根拠の弱い内容をバグとして作らない。観測した事実と推測は必ず分ける。

## 最初にやること

1. `production`との差分を確認する。
   ```bash
   git diff --stat production...HEAD
   git diff production...HEAD
   git log --oneline production..HEAD
   ```
2. 変更ファイル、コミット、影響しそうな画面・API・バッチ・設定・テストを整理する。
3. 差分が大きい場合は、サブエージェントを使って調査を分担する。
4. 差分だけでは判断できない箇所は周辺コード、呼び出し元、既存テスト、設定を読む。

## サブエージェントの使い方

変更点が多い、画面影響が複数ある、または1回の確認では見落としが出そうな場合は、積極的にサブエージェントを使う。

有効な分担例:

- **差分整理**: `diff-analyzer`でproduction差分を機能単位・コミット単位に整理する
- **コード品質レビュー**: `review-agent`で正しさ、保守性、例外処理、型、設計を確認する
- **画面・ユーザー影響レビュー**: UI変更、文言、状態遷移、権限別表示、既存画面への回帰を確認する
- **テスト観点レビュー**: 追加・修正すべきテスト、手動確認観点、リグレッション範囲を確認する
- **セキュリティ・本番準備レビュー**: 認証認可、機密情報、ログ、移行、後方互換性を確認する
- **コミット別レビュー**: 変更が多い場合は、各コミットの意図と差分を個別に確認する

各サブエージェントには1つの論点だけを持たせ、最後に結果を統合する。同じ指摘は重複させず、競合する見解がある場合は根拠を比較して判断する。

## レビューチェックリスト

### 要件・計画との整合性

- 実装が要件・依頼内容・計画と一致しているか
- 予定された機能・修正・制約がすべて反映されているか
- 計画からの逸脱が妥当な改善か、問題のある方向転換か
- 実装漏れ、過剰実装、意図しない仕様変更がないか

### 画面・ユーザー影響

- 使用中の画面、関連画面、導線、モーダル、フォーム、一覧、詳細、設定画面の変更が漏れなく報告されているか
- 表示文言、バリデーション、エラー表示、ローディング、空状態、権限別表示に不整合がないか
- 操作後の状態遷移、保存、更新、戻る、リロード、ページング、検索、フィルタが壊れていないか
- 既存ユーザーの操作フローに回帰や混乱がないか

### 可読性・保守性

- 変数名・関数名・クラス名が意図を明確に表しているか
- 関数・メソッドが単一責任を守っているか
- 重複したコードがないか
- コメントは不明瞭なロジックを補う用途に絞られているか
- マジックナンバーや魔法の文字列が適切に定数化されているか
- 早すぎる抽象化ではなく、必要な範囲で整理されているか

### エラーハンドリング

- 例外・エラーが適切に捕捉・処理されているか
- エラーメッセージが調査に十分な情報を持っているか
- 失敗時のリカバリー処理やフォールバックが考慮されているか
- ユーザーや呼び出し元が次に取るべき行動を判断できる返し方になっているか

### セキュリティ

- APIキー・パスワードなどの機密情報がハードコードされていないか
- ユーザー入力が適切にバリデーション・サニタイズされているか
- SQLインジェクション・XSSなどの脆弱性がないか
- 認証・認可のロジックが正しく実装されているか
- 権限境界、データ公開範囲、ログ出力に機密情報漏えいのリスクがないか

### パフォーマンス

- 不必要なループや再計算がないか
- N+1クエリ問題が発生していないか
- 適切なキャッシュやメモ化が使われているか
- 非同期処理が適切に扱われているか
- データ量・利用頻度が増えた場合も合理的に動作するか

### テスト

- 新しいロジックに対するテストがあるか
- エッジケース、境界値、null、空配列、権限分岐がテストされているか
- テストがモックの都合ではなく実際の振る舞いを検証しているか
- 重要な連携箇所に統合テストまたは手動確認観点があるか
- 既存テスト・関連テストの実行結果や未実行リスクが明示されているか

### 型・インターフェース設計

- 型定義が正確で過不足ないか
- `any` や型アサションの乱用がないか
- APIの引数・戻り値の型が適切に設計されているか
- 呼び出し元と呼び出し先の契約が破壊されていないか

### アーキテクチャ・統合

- 責務分離が明確で、周辺コードの設計と自然に統合されているか
- 既存のパターン・ヘルパー・設定方式を再利用しているか
- スケーラビリティ・拡張性に対して過不足ない設計判断になっているか
- 後方互換性が必要な箇所で破壊的変更が入っていないか

### 本番投入準備

- スキーマ変更・データ移行がある場合、移行手順とロールバック観点が考慮されているか
- 設定値・環境変数・ドキュメントの更新漏れがないか
- 監視・ログ・障害調査に必要な情報が不足していないか
- 明らかなバグ、データ損失、既存機能の破壊がないか

## 重大度の判断基準

- **Critical**: セキュリティ脆弱性、データ損失、壊れた主要機能、本番事故につながる問題
- **Important**: 要件漏れ、設計上の問題、重要なエラーハンドリング不足、テスト不足、回帰リスク
- **Minor**: 可読性、保守性、表示の細部、ドキュメント、軽微な改善

実害がある問題だけをCriticalに分類する。根拠が弱い場合は「確認事項」または「推測」として扱い、バグとして断定しない。

## 出力フォーマット

### 調査範囲

- 確認した差分範囲
- 読んだファイル、コミット、画面、テスト
- 使用したサブエージェントと担当観点

### 変更内容の網羅報告

- 機能単位またはコミット単位で、何が変わったか
- 使用中の画面や関連画面に関する機能変更
- 既存機能への影響がありそうな箇所

### Strengths / Good

良い実装や妥当な設計判断を、ファイル・行・具体的な理由つきで書く。

### Issues

#### Critical

必ず修正すべき問題。

#### Important

修正を強く推奨する問題。

#### Minor

細かい改善点。数が多くても省略しない。

各Issueには次を含める。

- **File:line**
- **問題**
- **なぜ問題か**
- **修正案**
- **根拠の強さ**: 観測 / 推測 / 確認事項

### Recommendations

コード品質、アーキテクチャ、テスト、手動確認、リリース前確認の推奨事項を書く。

### Assessment

- **Ready to merge?** `Yes` / `No` / `With fixes`
- **Reasoning:** 1〜2文で技術的な理由を書く

## 守ること

- 指摘数に人工的な上限を設けない。細かい問題も、実害や保守上の意味があるなら網羅的に挙げる。
- ただし根拠の弱いバグは作らない。観測できた事実、推測、確認事項を分ける。
- 読んでいないコードにはフィードバックしない。
- 「looks good」だけで済ませず、確認した観点と根拠を示す。
- 些細な好みやスタイルの違いをCriticalとして扱わない。
- 同じ問題を言い換えて重複させない。
- 最終的なマージ可否の判断を曖昧にしない。
